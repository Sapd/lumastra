# Exact-pinned + hash-pinned direct and transitive dependencies for the
# sonic-embedder sidecar, EXCLUDING torch/torchaudio, torch's CUDA-wheel
# dependencies, and networkx (see below).
#
# RESOLVED FOR: linux/x86_64, CPython 3.10 — the interpreter and platform the
# Dockerfile's digest-pinned base image actually runs
# (pytorch/pytorch:2.3.1-cuda12.1-cudnn8-runtime is Python 3.10.14; pytorch's
# own docker.Makefile at v2.3.1 pins PYTHON_VERSION ?= 3.10, and the preprod
# sidecar reports 3.10.14). Re-resolved 2026-09-15 with pip 26.2.1 inside a
# `python:3.10-slim` container run as `--platform linux/amd64`, NOT on the
# developer's Mac.
#
# This matters, and is not a formality: the 2026-09-14 pins were generated
# under Python 3.12 on macOS/arm64, and four of them declare
# `Requires-Python >= 3.11` (scipy 1.17.1, scikit-learn 1.9.1, networkx 3.6.1,
# websockets 17.1). Under an `==` pin pip filters every file of such a release
# as requires-python-incompatible, so `docker build` failed outright with
# "Could not find a version that satisfies the requirement scipy==1.17.1".
# The break stayed invisible because the running preprod sidecar image was
# built 2026-07-10, before those pins existed, and the CI deploy step does not
# recreate the sidecar. Anything that regenerates this file MUST resolve on
# Python 3.10 / linux x86_64 (see requirements.in for the recipe), or the
# image stops building again.
#
# Sources (see requirements.in):
#
#   msclap==1.3.4
#   librosa, soundfile, pyloudnorm, umap-learn, psycopg2-binary, scikit-learn,
#   fastapi, uvicorn[standard]        (the Dockerfile's previous >= floors)
#
# constrained to torch==2.3.1 + torchaudio==2.3.1 (the pytorch/pytorch base
# image's CUDA build) so the REST of the graph — transformers, numpy, etc. —
# resolves against what is actually installed, not whatever is newest on PyPI.
#
# torch and torchaudio are deliberately NOT listed below, even though they
# were part of that resolution: torch ships in the pytorch/pytorch base image
# as a CUDA build, and PyPI's plain `torch==2.3.1` is a CPU-only wheel with a
# DIFFERENT build than what's installed — an explicit `torch==` pin here that
# pip considers unsatisfied (e.g. because the installed version carries a
# local version segment like `2.3.1+cu121` that a bare `==2.3.1` specifier may
# not match) would silently downgrade the container to CPU-only inference.
# msclap's own metadata already declares `torch>=2.1.0,<3.0.0` /
# `torchaudio>=2.1.0`, which the already-installed CUDA build satisfies via
# ordinary range comparison (no local-version ambiguity) — leave it to that.
#
# For the same reason, `triton==2.3.1` and the twelve `nvidia-*-cu12` wheels
# are excluded too. They are NOT part of this sidecar's own dependency set:
# they surface only because a from-scratch linux/x86_64 resolution installs
# torch from PyPI, and it is the PyPI *wheel* that declares them (pytorch's
# setup.py adds those pins only when PYTORCH_EXTRA_INSTALL_REQUIREMENTS is set
# during a wheel build). The base image's CUDA runtime is what provides those
# libraries, and installing the pip copies on top would both bloat the image
# and risk shadowing them. The previous macOS-resolved file omitted them by
# accident — an arm64 resolution never sees them, since their markers are
# gated on `platform_system == "Linux" and platform_machine == "x86_64"`.
# Here the omission is deliberate: torch's pure-Python dependencies
# (filelock, fsspec, jinja2, markupsafe, mpmath, sympy, typing-extensions)
# ARE pinned below, as they were before — EXCEPT networkx, which joins the
# torch/torchaudio exclusion list for a different reason (below).
#
# `networkx` is deliberately NOT listed below either, even though — like
# sympy — it is only reachable via torch's own `networkx` dependency (this
# sidecar's own requirement roots never import it; grep embed.py/analyze.py/
# server.py/etc. and you won't find it). Pinning `networkx==3.4.2` here
# produced an image that built successfully (the hash-checked install
# succeeded) but was BROKEN AT RUNTIME: `import torch` (which imports
# `networkx`) raised `SyntaxError` inside
# `networkx/utils/configs.py:__new__`, building a dataclass whose field names
# come from the discovered `networkx.backends` entry points. The base image
# ships networkx 3.2.1 via conda AND carries a stale pip
# `networkx-3.3.dist-info` (INSTALLER=conda still owns the conda copy; the
# leftover dist-info is pip metadata pytorch's own image build left behind)
# whose `entry_points.txt` registers a `networkx.backends` entry point named
# `nx-loopback` (networkx's own test-dispatcher backend) — not a valid Python
# identifier. networkx 3.2.1 has no such entry-point-driven dataclass code,
# so it never trips; pinning ANY 3.4.x here reintroduces the broken code path
# against that same stale entry point. Excluding it lets the base image's
# conda-installed 3.2.1 stand, exactly like torch/torchaudio above — a build
# that exits 0 is NOT proof this works; only a runtime `import networkx` (or
# `import torch`, which imports it transitively) catches this.
#
# `typing-extensions` has the same duplicate-dist-info symptom (this file
# pins 4.16.0; the base ships 4.11.0 via conda, and an earlier pip resolution
# left a stale `typing_extensions-4.12.1.dist-info` around, so
# `importlib.metadata.version()` reports the stale one) but, unlike
# networkx, nothing in the graph builds runtime behavior off of
# typing-extensions' installed version or its entry points — torch only
# declares `typing-extensions>=4.8.0`, which 4.16.0 satisfies by ordinary
# range comparison, and it imports and runs cleanly. Left pinned deliberately
# — do not churn a pin that works just because its metadata symptom looks
# like networkx's.
#
# `exceptiongroup` is the one package that enters the graph at Python 3.10 and
# did not exist in the 3.12 resolution: anyio requires it under
# `python_version < "3.11"`. It is pinned below WITH that same marker (so the
# line becomes a no-op if this file is ever re-resolved on a newer base) even
# though the base image already ships it as a conda package
# (/opt/conda/conda-meta/exceptiongroup-1.2.0-py310h06a4308_0.json,
# INSTALLER=conda) and pip's already-satisfied short-circuit would have
# covered it. Pinning it explicitly keeps the file self-contained: a build in
# any environment that does NOT happen to preinstall it would otherwise fail
# hard under --require-hashes ("all requirements must have their versions
# pinned with ==") rather than resolve.
#
# HASH SOURCE: PyPI's own JSON API (`GET https://pypi.org/pypi/<name>/<version>/json`,
# `urls[].digests.sha256`) — the sha256 PyPI itself computed when each file was
# uploaded — not locally recomputed from downloaded bytes. `pip-compile
# --generate-hashes` was tried twice and stalls indefinitely here: it
# re-resolves the FULL graph (including transitive torch) and downloads full
# wheel bytes to hash them, and torch/transformers-adjacent wheels run to
# hundreds of MB each. Every uploaded artifact for each EXACT pinned version is
# included (every wheel across every platform/CPython, plus the sdist),
# mirroring pip-compile's own default --generate-hashes output shape, so the
# hash set is not scoped to the one interpreter that fetched it even though
# the VERSION resolution deliberately is.
#
